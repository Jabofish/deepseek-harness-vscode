# Development, testing and release

Use this guide to choose checks, run tests and report results. Setup and PR submission are in [Contributing (English)](../.github/CONTRIBUTING.md) / [贡献指南](../.github/CONTRIBUTING.zh-CN.md). Implementation rules are in the [architecture](architecture.en.md), [upstream contract](dsh-contract.en.md) and [capability matrix](capability-matrix.en.md).

## Development setup

Use the Node/pnpm requirements in the root [package.json](../package.json), and the VS Code requirement in the [extension manifest](../apps/extension/package.json). Install with `pnpm install --frozen-lockfile`; do not regenerate the lockfile as a setup workaround. Commands below run from the repository root.

Open that root in VS Code, create the ignored `.test-workspace/` directory for the launch configuration, and select **Run JaboDSH Extension**. F5 runs the `build` pre-launch task and starts an Extension Development Host; Ctrl+F5 runs without the debugger. `pnpm dev` watches extension and Webview builds. The launch configuration enables the development managed-runtime path; use disposable workspaces/sessions and check the selected connection settings before connecting.

If debugger attachment fails on an IPv6 probe, run without debugging first. The optional `node scripts/patch-js-debug-ipv6-probe.cjs` helper addresses the known single-address probe failure; confirm that diagnosis before modifying VS Code's installed debugger. Use `--restore` after an upstream fix or to undo the patch. Record an extension-host launch failure as a blocked check.

Shared TypeScript and specialised Vitest configuration lives in `config/`. Root `tsconfig.json`, `vitest.config.ts`, ESLint and Prettier files remain tool-discovery entrypoints. `apps/extension/media/` and companion resources are generated by the build; do not commit them.

## Choose validation by change

Use the rows that apply to your change.

| Change                                                                              | Required validation before review                                                                                                                                                                                                               |
| ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Documentation only, no runtime/build behaviour change                               | `pnpm docs:check`, `pnpm format:check`, `git diff --check`; follow links and read the changed instructions. If editing the documentation checker, also run `node --check scripts/check-docs.mjs` and `pnpm exec eslint scripts/check-docs.mjs`. |
| Application, UI, protocol, Adapter or build/tool behaviour                          | Regression tests at the affected boundary, then `pnpm check`, `pnpm build` and `git diff --check`.                                                                                                                                              |
| UI copy, styles, navigation or interaction                                          | Code checks above plus the affected [manual scenarios](#manual-interaction-checks); check both locales for copy changes.                                                                                                                        |
| DSH contract, connection, process ownership or companion                            | Code checks above plus an [isolated native DSH run](#isolated-native-dsh) for each claimed affected version, and Electron/manual checks when Host integration or interaction changes.                                                           |
| Long conversations, transcript windows, backpressure, grammars or attachment bounds | Code checks above plus `pnpm test:stress`; for a performance claim, record a reproducible real baseline and the measured processes/workload.                                                                                                    |

Missing runtime, credentials, a display server or another OS need not prevent a draft contribution. State what was not run and why, and keep the corresponding acceptance open. Do not replace a required live/manual check with a fixture result or mark an incompletely verified capability `DONE`.

For documentation-only work, the local documentation checks are sufficient. PR CI continues to run the configured checks.

## Automated tests

| Command                                                       | What it does                                                                                    |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `pnpm exec vitest run packages/timeline/test/reducer.spec.ts` | Example of running one existing regression file; substitute the relevant test path.             |
| `pnpm test:changed`                                           | Affected tests for local uncommitted changes plus the fixed contract selection, deduplicated.   |
| `pnpm test:changed upstream/main`                             | Tests affected by a branch comparison plus fixed contracts; fetch the actual base remote first. |
| `pnpm test:changed --list`                                    | Preview that selection without running the tests.                                               |
| `pnpm test:contracts`                                         | Fixed filesystem, style, user-control, schema, route and build contracts.                       |
| `pnpm test`                                                   | Full default Vitest suite. Stress tests and opt-in live scenarios are excluded or skipped.      |
| `pnpm check`                                                  | Format, documentation, i18n, lint, typecheck and the default automated suite.                   |
| `pnpm build`                                                  | Build the companion resources, Webview and extension.                                           |
| `pnpm test:stress`                                            | Separate serial stress suite, including large history/window and memory probes.                 |
| `pnpm test:ui-stability`                                      | Selected functional UI suites, then production App/Timeline scenarios in isolated Chromium.     |
| `pnpm test:billing-evidence`                                  | Separate billing evidence suite configured in `config/`; use when that evidence path changes.   |

Run the applicable stress, native DSH and VS Code checks separately. Inspect `git status --short` alongside `git diff --check` so unrelated or generated files do not enter the PR.

`pnpm test:ui-stability` first runs the functional UI suites selected in `scripts/ui-behavior-suites.mjs`, including input, queue admission, ownership, interactions, focus and scroll regressions. It then uses an installed Chrome, Chromium or Edge to exercise production App/Timeline behavior. Set `DSH_UI_BROWSER` to its executable when automatic discovery does not find it. The runner creates a temporary browser profile and a loopback fixture server, then releases both. Browser cases cover common delivery, session, attachment, model, keyboard and narrow-window flows alongside output, history insertion, nested details, visibility recovery, delayed images and navigation. Set `DSH_UI_SCENARIO` to a reported scenario name to reproduce it separately, or `DSH_UI_GROUP=daily` for full-App browser cases only. Filtered runs omit the functional suites. Unknown names fail instead of reporting success with no coverage. Functional results, browser observations and failure screenshots remain under the run's `artifacts/ui-stability-browser/` directory.

Keep browser stability cases tied to reader behaviour:

- Verify the setup and action have an effect: input actually leaves the tail, an inner scrollport actually moves, or incoming output makes a short conversation scrollable. A no-op action must not pass as coverage.
- Assert the visible answer, retained reading source and its observed position. A zero bottom gap alone can hide a blank scroll range. Compare with the reader's position before the action; do not require a particular DOM structure, fixed row height, exact offset or implementation frame count.
- Wait for geometry to become quiet and finite animations to finish. Observe reading positions after rendering so a jump followed by a return cannot pass solely on its final state. Keep observation bounds and geometric tolerances separate from product acceptance values.
- Keep selectors in the fixture adapter. Retain JSON observations and failure screenshots under `artifacts/ui-stability-browser/`; verify defect regressions against a reproducing revision or a controlled test-build mutation when practical.

The [daily UI inventory](ui-scenarios.en.md) lists behavior coverage and gaps. The browser runner also mounts the production App, Store and protocol client against a controlled Host fixture. These controlled browser scenarios do not replace real VS Code/DSH or assistive-technology acceptance.

[CI](../.github/workflows/ci.yml) runs lint, static checks and tests on Linux, and builds on Linux, Windows and macOS. PRs use `pnpm test:changed` against their base branch; pushes to `main` and manual workflow runs execute the default suite in shards. The [release workflow](../.github/workflows/build-vsix.yml) runs `pnpm check` before packaging. Do not require contributors to run three operating systems locally.

### Regression tests

- Test each new behaviour, regression and failure branch near its implementation. Add a representative cross-layer case when the interaction between layers matters.
- Use colocated `*.spec.ts`/`*.spec.tsx`; keep independent heavy cases in `*.stress.spec.ts(x)`, or tag heavy cases `stress` in mixed files. The default config excludes both forms; the stress config runs them separately.
- Use fake time for backoff/debounce logic. Large loads use generated fixtures, never real conversation logs. Do not present virtual-clock latency as measured UI latency or CPU time.
- Version fixtures identify their exact upstream tag/commit, source file and type. Share version-selection/harness helpers in `packages/dsh-adapter/test/support/`; add only that version's contract differences. Do not accept unknown wire changes by updating snapshots.
- Dependency-based selection can miss CSS, fixture and path-read dependencies. Register new filesystem-read contracts in `scripts/test-changed.mjs` so affected-test runs include them.

### Required failure paths

Cover the paths affected by the change: missing/unsupported DSH and failed candidates; concurrent connect/cancel; early process exit and readiness/port failures; malformed RPC/frames, timeout and disconnect; duplicate/out-of-order/gapped delivery; stale replies, settings rollback and unavailable capabilities; resource release on failure/cancel/disposal. Attachment/export changes also cover size, overwrite, Zip Slip, symlinks, remote filesystem boundaries and cancellation cleanup. Keep the existing TODO acceptance criteria and strict types intact.

Test user controls from the real Store through the protocol client and Host router to the handler. Advisory model/catalogue failures must not block sending, stopping or answering. Preserve exact model/permission selections; stale generations and identical request IDs in different windows must not cross ownership boundaries. After trust is revoked, stop/refusal/cancel remain available while actions that execute files/tools stay guarded.

## Isolated native DSH

These tests are opt-in. Start with the connection smoke below. Choose an installed exact supported runtime from the [contract](dsh-contract.en.md); replace both placeholders. The harness owns its temporary workspace/home and only its own process handles. Do not point tests at a production profile or install/update a global DSH merely to run the default suite.

PowerShell, in a fresh terminal:

```powershell
$env:DSH_LIVE_SMOKE = '1'
$env:DSH_LIVE_RUNTIME = '<dsh-executable>'
$env:DSH_LIVE_RUNTIME_VERSION = '<exact-supported-version>'
pnpm exec vitest run tests/live-dsh/run.spec.ts
```

POSIX shell, with variables scoped to this command:

```sh
DSH_LIVE_SMOKE=1 DSH_LIVE_RUNTIME='<dsh-executable>' DSH_LIVE_RUNTIME_VERSION='<exact-supported-version>' pnpm exec vitest run tests/live-dsh/run.spec.ts
```

Then select the live files affected by the change, or run `pnpm exec vitest run tests/live-dsh` when their prerequisites are met. Record the actual installed version and per-scenario pass/skip results: some suites support only specific runtime families. The native `question-lifecycle.spec.ts` probe resolves peer packages relative to a package-local executable path; a bare command or global shim may not meet that layout. Use a compatible installed runtime layout for that probe. Record unsupported layouts as blocked.

Empty homes cover handshake, RPC and lifecycle paths; history-dependent scenarios need an explicit sanitised disposable fixture home directly under the OS temp directory (`DSH_LIVE_HISTORY_FIXTURE_HOME`). Without one, history/page/tool/export/subagent/review scenarios may skip. List skipped scenarios and their reasons in the results.

For Windows installer changes, the default suite includes real file-sharing violations and owned descendant cleanup. Run `tests/live-dsh/windows-runtime-installation.spec.ts` separately with `DSH_LIVE_INSTALLATION=1`, `DSH_LIVE_INSTALL_FROM` and `DSH_LIVE_INSTALL_TO` set to exact package versions, and `DSH_LIVE_NPM_CLI` set to npm's `bin/npm-cli.js`. It installs both versions into a disposable global prefix, verifies the actual launchers and `npm list --global`, and removes that prefix. The test uses npm's offline cache; populate the cache in an isolated prefix first if the chosen packages are unavailable. This does not exercise the Settings installation flow in a real VS Code window.

`DSH_LIVE_EDITOR_COMPANION=1` additionally exercises installation of the bundled companion in the isolated runtime. Windows `.cmd` shims are resolved by the harness, not by `shell: true`. Live files run serially with a managed lock; verify owned process and port cleanup even on failure. Close the PowerShell terminal after an opt-in run, or unset these variables before normal checks so they do not unexpectedly enable live tests.

## VS Code / Electron runner

Build first. The runner uses a locally installed VS Code executable that meets the [extension's minimum version](../apps/extension/package.json); it does not download an editor. On Windows, pass `Code.exe` directly rather than `bin/code.cmd`. Replace the executable placeholder and use a fresh terminal. PowerShell:

```powershell
pnpm build
$env:DSH_VSCODE_E2E_EXECUTABLE = '<path-to-Code-executable>'
$env:DSH_VSCODE_E2E_MODE = 'attach-only'
node --experimental-transform-types tests/vscode-e2e/run.ts
```

POSIX shell:

```sh
pnpm build
DSH_VSCODE_E2E_EXECUTABLE='<path-to-Code-executable>' DSH_VSCODE_E2E_MODE=attach-only node --experimental-transform-types tests/vscode-e2e/run.ts
```

The default `attach-only` mode drives a real Extension Host against a controlled loopback fixture. It covers activation, commands and transport. Use managed mode for the real DSH launch path and the manual scenarios below for chat interaction.

For native launch paths, set `DSH_VSCODE_E2E_MODE=managed` or `auto`, plus `DSH_VSCODE_E2E_RUNTIME` to the chosen runtime, in the same environment as the command. Both modes create a disposable `DSH_HOME`; the suite checks ownership and that the runtime actually wrote to that home. `auto` also refuses known serving external endpoints before starting, but cannot prove that the OS process-scan source contains no other DSH: use an environment without unrelated instances, and never stop a user's instance to make a test pass.

Optional `DSH_VSCODE_E2E_COMPANION=1` checks supported companion installation/reconnect paths; `DSH_VSCODE_E2E_INVALID_SETTINGS=1` checks activation with invalid settings. Report which mode/options ran. These automated checks do not observe every focus, theme, sidebar or chat behaviour; use the manual checks below for affected interactions. Report an editor update lock or unavailable display as a blocker.

## Manual interaction checks

Use the development host with disposable data and the intended connection mode. Test the affected scenario's success and relevant failure/retry path; there is no requirement to run unrelated scenarios for every PR.

| Affected area                    | Exercise and observe                                                                                                                                                                                                             |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Composer and controls            | Send, stream, cancel/stop, retry a failed operation; answer/refuse a question or approval; ensure the control reaches DSH and the pending UI settles. Check that slow advisory reads do not block controls.                      |
| Navigation and multiple panels   | Switch sessions during output; open sidebar and editor panels, split, hide/reveal, close/reopen and reload. Check no stale content, cross-session replies or duplicate subscriptions.                                            |
| History and rendering            | Load older history, follow a live tail, expand/copy long text, code and tables; check content/order/scroll position and absence of repeated full-body loading or flashes.                                                        |
| Connection, process or companion | Exercise the changed connect/reconnect/cancel/failure path; verify external DSH survives, owned resources release, and companion disable/read-only/Undo behaviour when affected.                                                 |
| Appearance and accessibility     | Check changed UI in English/Chinese, narrow sidebar and split editor, light/dark/high-contrast themes, keyboard/focus and Reduced Motion. Check accessible names/announcements; use a screen reader when those semantics change. |
| Files and trust                  | Check the changed picker/export/attachment action, cancel it, test denied trust/path access, and verify failures are visible without exposing private data.                                                                      |

For visible changes, capture the relevant before/after state with sensitive data removed. For controls, record the native handler result along with the UI state. Real model calls are only needed when the changed behaviour requires them; use explicitly chosen development credentials, and report when a controlled producer/fixture was used instead.

## Report test results

Use the relevant lines in a PR, review or bug follow-up, in either language:

```text
Revision / scope: <commit or working-tree scope; relevant capability ID if any>
Environment: <OS, Node/pnpm; VS Code, extension and exact DSH version/mode when used>
Automated: <command -> pass/fail; skipped count/reason when relevant>
Manual: <steps -> expected and observed result; screenshot/recording if useful>
Not run / blocked: <check, reason and remaining acceptance>
```

For regressions, include the smallest reproducer and before/after behaviour. For performance, add workload/history size, visible/hidden panels, hardware, duration and measured process scope. Report cumulative CPU time in CPU seconds separately from wall time; identify whether the DSH backend is included. Distinguish samples/peaks from totals and native/model runs from deterministic fixtures. For a single comparison, report the observed values and test conditions.

Keep model prompts, tool bodies, credentials, tokens and private paths out of shared logs and screenshots. Prefer **JaboDSH: Show Redacted Diagnostics**; inspect any output before posting it. Vulnerabilities follow the [private security policy](../.github/SECURITY.md).

`DONE` requires implementation, applicable automated checks and the necessary native DSH/UI evidence. Otherwise retain `PARTIAL` and state the gap. Keep capability scope and limits in the matrix; put test logs and benchmark results in PRs or release records. Update the [owning document](README.md) when a rule changes, and keep exact upstream version lists in the contract.

## Release validation

Maintainers handle releases. An authorised release requires full checks and three-platform CI, the applicable native/UI tests, stress results for changed performance paths, and security/packaging checks.

Transcript rendering changes need the stress suite's large-history coverage, including at least 10,000 timeline nodes; activation must stay idle until needed and resident work/buffers must remain bounded. Validate resources and displayed content as well as throughput.

When packaging is in scope, `pnpm package:vsix` builds the VSIX. From `apps/extension/`, `pnpm exec vsce ls --no-dependencies` lists included files: inspect the allowlist, licences, relative source paths and absence of Webview sourcemaps/secrets/temp files. Use local builds for clean-profile install/uninstall, upgrade and rollback checks before publication.

Tagged releases run quality checks and five platform packages. A separate job verifies the universal VSIX checksum and signs its build provenance with `id-token: write` and `attestations: write`; packaging jobs have read-only repository access. GitHub Release and Marketplace jobs wait for packaging and attestation, then check the universal VSIX checksum again before publication. After publication, verify the tag's commit, terminal workflow results and GitHub release asset metadata: expected names, uploaded state, sizes and digests. Do not download published release assets for routine validation or repeat installation checks after publication.

To validate workflow changes without publishing, manually run `build-vsix.yml` on the reviewed branch with `publish_marketplace=false`. Check all five packages and the attestation job reached success, and both publication jobs were skipped. Inspect the workflow logs for checksum verification and provenance identifying the reviewed commit and workflow run. Manual validation does not execute the tag-only GitHub Release job; verify that job on the next authorised release.

Stable `v<major>.<minor>.<patch>` tags automatically publish the checked universal VSIX to Marketplace after quality, packaging and provenance succeed. The tagged commit must belong to `main`. A manual `build-vsix.yml` run on `main` with `publish_marketplace=true` supports recovery and authentication verification; the default remains false for packaging-only runs. Verify the exact Marketplace version independently, excluding versions still under validation. An existing version is skipped after authentication rather than uploaded again.

Configure Trusted Publishing once in the `Jabofish` publisher: repository owner `Jabofish`, repository `deepseek-harness-vscode`, workflow `build-vsix.yml`, environment `marketplace`. The publishing job requests `id-token: write` at job scope; `vsce` exchanges it for a short-lived Marketplace credential without reading `VSCE_PAT`. Missing OIDC context or a mismatched policy fails before upload. Keep dependency lifecycle scripts disabled in that job.

The GitHub `marketplace` environment allows only the `main` branch and `v*` tags, with no per-release reviewer gate for automatic publishing. Declaring `environment: marketplace` does not configure these restrictions; inspect the repository environment settings separately. Recheck the Marketplace policy if the repository, workflow filename or environment changes. See Microsoft's [Trusted Publishing guide](https://code.visualstudio.com/api/working-with-extensions/publishing-extension#publish-with-github-actions-and-trusted-publishing).
